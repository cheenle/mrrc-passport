# 08. 架构决策（ART 0513）

每条决策都写同样五段，因为决策里真正有用的部分很少是决策本身：

- **Problem（问题）** —— 逼出这个选择的故障或约束；
- **Alternatives（备选）** —— 被否决的方案，以及否决它的那次测量；
- **Decision（决策）** —— 一句话，可被引用；
- **Consequences（后果）** —— 现在要付的代价，包括"永远不许做什么"；
- **Amendments（修订）** —— 后来的事实，追加并带日期（第 `00` 章 §V4）。

AD 永不重新编号、永不删除。决策被推翻时，推翻过程以"点名那一次测量"的修订形式记在这里，
`Status` 按第 `00` 章 §V5 的阶梯诚实地往下走。

## AD-001：一条会话、一个 socket —— `/WSterminal`

| 属性 | 值 |
| --- | --- |
| 类型 | 架构 / 协议 |
| 状态 | Implemented，field-exercised（2026-11-21） |
| 决策 | 一条 TLS/WebSocket 会话同时承载文本控制与三条二进制通道：`0x00` RX 音频、`0x01` TX 音频、`0x02` 频谱。载荷首字节是通道号，其余是旧端点的载荷原样。 |

**问题。** 参考服务器暴露四个独立端点。在这块板子上每一条都是 TLS 会话，而一条 TLS 会话
就是一次 16 KB 连续分配（`docs/design-v1.md` 4.3）。四条放不下。比放不下更糟的是：发射路径
必须在按键那一刻拆掉下行 socket、重建上行 socket——恰好在操作者开始说话时留出一段 settle
空档，每次都丢掉第一个音节。

**备选。** (a) 保留四条 socket、缩小 TLS 缓冲——实测 `largest` 掉到 18 KB，低于握手下限，
表现为反复重连。(b) 按键时惰性打开 TX socket、释放时关闭——那正是 settle 空档本身，而且
让按键依赖一次 400 ms 的握手。(c) 自创一套更精简的终端协议——于是角色检查、PTT 所有者仲裁
与状态机会在两套实现之间漂移，服务器四端点时期那些 PTT 竞态就是这样来的。

**决策。** 一条会话、一个 socket、带通道前缀的二进制帧。

**后果。**
- 服务器的角色/令牌检查与 PTT 所有者仲裁原样生效；固件是**继承**它们，而不是重新实现。
- 媒体拥塞**不得**被当成控制链路故障：丢一个音频或频谱帧是常态，为此杀掉 socket 不是
  （`05` NFR-024，guardian 规则 `single-terminal-endpoint`）。
- 频谱在这条 socket 上是奢侈品：发射期间降档/丢弃，而不是排队——40 KB 的频谱积压会拖住上行。
- 所有旧客户端（浏览器、iOS、Android）保留各自端点——这是终端专属决策，不是协议迁移。

## AD-002：只走 PCM16 —— 本镜像里没有 Opus 解码器

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 资源 |
| 状态 | Implemented，field-exercised（2026-11-19） |
| 决策 | 终端声明 PCM16 档位并直接流原始 16 位单声道；服务器负责把它自己 48 kHz 的总线降到这个档位。 |

**问题。** Opus 看起来是免费的——码率从 256 kbps 降到 12 kbps——但在一颗 160 MHz 单核、
无 FPU 的芯片上解码器不是免费的。本机实测：**约 24 KB 堆、约 60% 的单核**。当时 `free`
是 49–55 KB、`largest` 是 44 KB；24 KB 就是 TLS 握手所依赖余量的一半。

**备选。** (a) 保留 Opus 并把绘制缓冲降到 8 行——UI 冲到 58% CPU 且瀑布退化成插值。
(b) 只在不动显示时解码——显示一直开着。(c) 按方向分别协商——上行什么也得不到，瓶颈从来
不是链路：同一 AP 上参考客户端证明下行上限由本设备的队列决定，两种方案下都约 31 KB/s 音频。

**决策。** PCM16，16 kHz 单声道，上行每 20 ms 帧 641 B。

**后果。**
- 带宽变成每方向 256 kbps，而且这**不是**瓶颈（实测 `31.3 KB/s` 音频 + `17.8 KB/s` 频谱 =
  `50.2 KB/s` 总量，与同一 AP 上的参考客户端相同）。
- 重采样落到服务器；只会 Opus 的服务器无法服务这个终端，这是刻意的、写明的不可兼容。
- `main/` 下不得再出现 `opus` 符号——guardian 规则 `no-opus-in-firmware` 存在，是因为
  "其实可以压缩一下"是一个反复出现、且听起来很合理的念头。

## AD-003：编解码器固定在 16 kHz，永久

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 硬件事实 |
| 状态 | Implemented，hardware-verified（2026-11-18） |
| 决策 | ES8311 与两条 I2S 方向在固件生命周期内都跑 16 kHz；运行期永不调用 `bsp_audio_set_format`。 |

**问题。** 这块板子上 48 kHz 采集不是慢，而是**聋**。同一段采集代码、同一个麦克风，只改
编解码器速率：

| 编解码器速率 | PCM 峰值（满量程 32767） |
| --- | ---: |
| 48 000 Hz | **468** |
| 16 000 Hz | **12 708** |

差 27 倍。上游 demo（`ref/ai-passport`）只跑过 16 kHz，所以 48 kHz 采集从未被验证过。

**备选。** (a) 48 kHz 采集 + 30 dB 软件增益——信号在，ADC 噪声也在，而且增益加在噪声底之上
的量化值上；"麦克风太小"那三天就是这么浪费掉的。(b) 两个编解码器实例——这块板子上 ES8311
的 MCLK/BCLK/WS 是采集与播放共用的，"48 kHz 进、16 kHz 出"在这块硬件上不存在。(c) 按会话
重配——`bsp_audio_set_format` 会删除并重建编解码器：一声可听爆音加几十毫秒断流，正好发生在
按键时刻。

**决策。** 固定 16 kHz，两条路都用软件桥接：下行 48 → 16 kHz 做 3:1 抽取（三点平均兼作
抗混叠）；上行 16 → 48 kHz 做 3:1 零阶保持，服务器再往后续重采样。

**后果。**
- 时钟没有 APLL：MCLK 来自 PLL_F160M 经 39 分频，得到 **16.03 kHz——快 0.16%**。30 分钟
  会耗掉约一秒的缓冲，这就是为什么短时间的收听证不了任何事（`05` NFR-027）。
- 上行 8 kHz 以上的混叠无法避免，且被接受：电台自己的 TX 带宽滤波远低于它。
- 将来任何改动编解码器速率都是硬件级主张，必须带着峰值测量来，不能只引数据手册。

## AD-004：上行拥塞时丢一帧，而不是丢会话

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 可靠性 |
| 状态 | Implemented，field-exercised（2026-11-22） |
| 决策 | 设备：上行单帧写超时 100 ms。服务器：持键的 socket 不接收下行音频。两半都是必需的；只有一半修不好这个故障。 |

**问题。** "PTT 按几秒就自己松开"被三次诊断成按键故障。按键日志给出了相反的证据：一次按下
持续 16.5 秒，没有释放事件。死掉的是上行：

```
tx: frames=78 sendfail=71
esp_transport_write() returned 0, timeout_ms=1000
net: /WSterminal error -> disconnected -> Failed to send the buffer
每约 2 秒重连一次
```

根因：服务器把电台的 RX 音频扇出到终端 socket，**完全不看 PTT 状态**。于是发射期间这条 TCP
同时承载 **32 KB/s 上行**（PCM16 麦克风）与 **30 KB/s 下行**（设备已 mute 并丢弃的音频）。
移动链路上下行占满窗口，上行写阻塞一秒，websocket 客户端把写失败当致命错误拆掉会话——TX
指示灯熄灭，操作者读到的就是"按键自己松了"。

**备选。** (a) 只做客户端 mute——设备本来就 mute 了，服务器照发，那些帧照样吃窗口。
(b) 新增"关闭音频"档位——服务器两条能力解析只认 `pcm16`/`pcm48`，为了省一个 `continue`
做双向协议改动。(c) 提高写超时——把 1 秒阻塞换成更长的阻塞，两秒后再重连。
(d) 按键期间关掉下行 socket——AD-001 的 settle 空档又回来了。

**决策。** 服务器跳过持键 socket 的下行音频（半双工：电台本来不在接收，那些帧不是丢失——
根本没有产生）；设备丢掉 100 ms 内写不出去的帧。

**后果。**
- 100 ms 内写不出去的帧，后面四帧也写不出去；快速失败只丢一帧，而不是把发射循环拖成
  2 帧/秒、而麦克风仍在按 50 帧/秒产数据。
- 持键 socket 的下行静默**不得**计入丢弃，且发射很多的会话实时比读低是**正确**结果
  （服务器侧记账，记录在 `mrrc_modern/SDD/` AD-040）。
- 修复后实测，一次 30.5 秒发射：`frames=1500 sendfail=0 readfail=0`、50.0 帧/秒、最慢
  单帧 27.9 ms、`slow=0`，发射窗口内 W/E 日志行**零条**。
- 两半中任何一半都可能被将来的改动"临时"去掉，而单独看都很无辜。guardian 规则
  `half-duplex-context` 存在的目的，就是让这个耦合在调用处可见。

## AD-005：瀑布用 8 位调色板索引存储

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 资源 |
| 状态 | Implemented，field-exercised（2026-11-22） |
| 决策 | 240×40 的瀑布每像素存一个字节，作为 256 项调色板的索引；`heat_init()` 在第一个消费者之前把色带填好。 |

**问题。** `uint16_t s_wf_buf[240 × 40]` 是 19 200 B `.bss`——应用里最大的单块——而
`largest` 只有 27–42 KB，面对 16 KB 的握手下限。

**备选。** (a) 历史减到 24 行——丢掉那 1–2 分钟、正是瀑布有用之处的时间窗。
(b) 只存轨迹、砍掉瀑布——瀑布正是这个设备存在的理由。(c) 保留 RGB565、按需展开区域——
那是 4.8 KB 临时缓冲再加每次刷新拷贝，实测不比索引路径好。

**决策。** 每像素一字节存索引，由 LVGL 在混合时查表。

| | 之前 | 之后 |
| --- | ---: | ---: |
| 瀑布缓冲 | 19 200 B | **10 624 B**（1 024 调色板 + 9 600 索引） |
| 稳态 `free` | 48 KB | **57–59 KB** |
| 稳态 `largest` | 27–42 KB | **38–48 KB** |
| 代价 | — | 1–2 个 CPU 点 |

**后果。**
- `largest` 涨了 11 KB，那才是 TLS 握手真正需要的；`free` 涨 9 KB 是这次结果里次要的一半。
- 顺序是承重的：在 `heat_init()` 之前读调色板会让每一行都黑，而症状看起来像 canvas 的 bug
  ——所以 guardian 规则 `palette-before-heat-init` 用 `order` 而不是 `pattern`：没有任何
  单独一行是错的。
- 轨迹仍然用 RGB565 点，只有瀑布搬了家。谁把两种格式"统一"一下，19 200 B 就回来了。

## AD-006：配网写 NVS，不写 Kconfig

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 可运维性 |
| 状态 | Implemented，field-exercised（2026-11-21） |
| 决策 | Kconfig 提供编译期默认值；NVS 保存最后一次配网得到的值，且永远优先。 |

**问题。** 凭证住在被 gitignore 的 `sdkconfig.defaults.local`，所以换网络等于重新编译。现场
没有重新编译这回事：设备在别人手里，没有串口控制台，也没有已知网络——Wi-Fi 一变，它首先要
做到的是**不需要**一台电脑就能救回来。

**备选。** (a) 硬编码凭证——否决：源码公开发布，密码会跟着 fork 走。(b) 在 flash 上放配置
文件——那就是多几步、且没有磨损均衡的 NVS。(c) 只留强制门户、没有回退——否决：已存网络仍
可用的设备永远不该需要门户。

**决策。** SoftAP 配网写 NVS；Kconfig 是默认值，只在 NVS 没有值时被采用。

**后果。**
- 配网永远不需要重新编译，重刷也不会丢凭证（除非擦掉该分区）。
- 优先级必须单向且可在一个模块里看清：多一个 NVS 写入者，就是配好的网络在重刷后悄悄回退的
  原因（guardian 规则 `nvs-single-namespace`；键所有权测试断言没有哪个键有两个写入者）。
- 保存失败必须让操作者观察到，不能静默——这就是 `docs/provisioning.md` 里专门有一节
  "如果保存失败"的原因。
- 触发条件与机制同等重要：网络不可达时门户必须出现，而正在工作的会话绝不能被它劫持。

## AD-007：多个网络，按音频健康度而不是信号强度选择

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / 可用性 |
| 状态 | Implemented，field-exercised（2026-11-22） |
| 决策 | 最多三组 (SSID, 密码)；开机优先上次可用网络；会话中切换由音频健康度触发，绝不只看 RSSI。 |

**问题。** 这个终端用在没有单一可靠接入点的地方——火车上通过手机热点实测 **6.5–12% 丢包、
RTT 峰值 6–10 秒**。直觉代理量 RSSI 被实测证伪：一个 **−25 dBm** 的接入点，信号完美，却在
丢约 10% 的包。

**备选。** (a) 永远连最强的——那就是 −25 dBm 这个反例。(b) 每次开机让用户选——设备通常
在口袋里开机。(c) 永远重试上一个网络——一个坏网络就能把终端锁死到电池耗尽。

**决策。** 维护一张短列表，记住曾经可用的，按观察到的音频健康度（持续帧丢失 / underrun）
切换，RSSI 只用于开机时给候选排序。

**后果。**
- "连上了"不等于"可用"：成功判据是健康度指标，不是关联事件（`05` NFR-010）。
- 一次切换要重新关联并重建 `/WSterminal`，所以必须稀少且带迟滞保护；来回抖动的切换比一个
  差网络更糟。
- 缓冲解决不了移动场景（十秒 32 KB/s 是 320 KB，而 SRAM 只有 400 KB），所以目标被写成
  **优雅降级**，不是连续性（`05` NFR-008）。

## AD-008：旋钮六个档位，以 OK 双击上报

| 属性 | 值 |
| --- | --- |
| 类型 | 设计 / UI |
| 状态 | Implemented，field-exercised（2026-11-22） |
| 决策 | 每个旋钮档位变化都以一次 OK 双击上报；旋转因此可以循环六项设置（STEP、FIL、MIC、VOL……），UP/DOWN 恢复为纯调频。 |

**问题。** 四档时可以给每个档位映射独立的键事件，但可区分的事件已经用尽：服务器与显示都
当作"循环当前选中项"的唯一手势，就是 OK 双击。

**备选。** (a) 六个位置只用四组——面板有六个位置，用四个是操作者看不见的谎。
(b) 发一个专门的"cycle"事件——为一个 UI 细节改服务器协议。(c) 不用 OK 语义的 press→press
——实测 250–420 ms，与两次调频点按完全重叠，按设计就无法区分。

**决策。** 旋转付一次双击事件的代价；UP/DOWN 保持纯调频。

**后果。**
- 这个映射是刻意有损的：设备无法向服务器表达"旋转"，所以将来任何旋钮手势要么落进既有键
  词汇，要么就是一次协议改动。
- 250–420 ms 是否决方案 (c) 的那个数字；它记在这里，是为了这个方法不要每隔几个月被重试一次。
- 循环是**本地** UI 动作，所以慢链路或忙链路都不会延迟指示——可见状态在请求发出之前就已经变了。
