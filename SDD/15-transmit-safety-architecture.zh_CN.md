# 15. 发射安全架构（ART 0535）

发射安全单独成章，理由和服务器那边单独成章一样：这条性质散布在音频路径、socket、按键处理
与操作者预期之间，没有任何一个文件拥有它。一次看起来局部的改动——一个超时、一个增益、一张
滤波表——就可能让电台在无物可送时被键控，或者让指示灯亮着而实际已经停止发射。

固件自己的贡献很小，所以这一章主要在讲**这个贡献的边界**：哪些事本设备可以独自保证，哪些
它交给服务器与电台。

## 15.1 分层模型

只有当每一层都能**停**，发射才是安全的：

| # | 层 | 所有者 | 它保证什么 | 它管不了什么 |
| --- | --- | --- | --- | --- |
| L0 | 操作者手势 | 固件（`keys_task`） | 按下上报一次、松开上报一次，丢失的释放被当成释放上报 | socket 已经没了时，什么都保证不了 |
| L1 | 会话状态 | 固件（`mrrc_net.c`） | 只有会话建立**且**服务器确认按键之后才产生 TX 帧 | 服务器接受了它用不上的帧时，什么都保证不了 |
| L2 | 帧节拍 | 固件（`mrrc_audio.c`、`mrrc_tx.c`） | 20 ms 节拍、每次写只有一帧在途、100 ms 写不出去的帧被丢弃 | 重传——没有重传，而且加上会更糟 |
| L3 | socket 活性 | 服务器 + 固件 | 死会话被检测到并强制回 RX，而不是留在键控状态 | 物理载波——如果电台忽略释放 |
| L4 | 电平与调制 | 固件（编解码器）+ 服务器（增益） | 样本无削波地到达电台，电平为操作者设置的值 | 电台拿它做什么 |
| L5 | 电台 TOT | 电台 | 无论上面发生什么，到点丢弃载波 | 它之上的任何东西 |

这张表里有两条是决策，不是观察：

- **"停"永远不被门控。** 每一层都可以因为某个原因拒绝**开始**发射（没有会话、没有编解码器、
  档位不对），但任何一层都不得拒绝停止。正是这个不对称，让整个栈可以被安全地改动。
- **最后一道防线不在固件里。** 固件无法给一台它联系不上的电台解键；`05` NFR-017（不允许
  无声载波）讲的是拒绝键控，不是熬过断链。电台的 TOT 是唯一有保证的停止手段，所以发射路径
  被设计成**朝静默的方向失效**。

## 15.2 前置条件：设备可以拒绝发射

键控需要以下全部成立，按键时按此顺序检查：

1. `/WSterminal` 会话在，且已完成音频能力声明（AD-001、AD-002）；
2. 编解码器跑在 16 kHz，且麦克风路径自开机以来至少产生过一帧（AD-003——键控一台编解码器
   已死的电台，就是无声载波）；
3. 上行当前未被另一个所有者的发射占用：服务器的按键仲裁是权威，设备不得乐观键控；
4. 操作者的按键状态与上报状态一致——在设备仍处于"键控中"时到达的释放，被当作释放处理，
   绝不排队。

以上任何一条不成立都是**可见的**：TX 指示不亮，串口留一行指出缺了哪个条件。静默拒绝与死键
无法区分，而这个设备已经因为这一点把一个故障误诊过一次（第 `00` 章 §0.1 第三行）。

## 15.3 释放是"发了就不管"

释放是一次写，什么都不等：

- 没有校验循环、没有"电台真的解键了吗"的重试、释放路径里没有延时——guardian 规则
  `ptt-release-never-blocks`（`05` NFR-013）；
- 理由不是客气：校验循环出问题时，代价是数百毫秒的**载波粘滞**，那是本设备能制造的最坏故障；
- 键控粘滞检测属于可观测性（L3），不属于释放路径。

固件上报释放并忘掉它。写失败就记录日志，且下一次会话建立时强制 RX；设备从不保留"可能还在
键控"的状态，因为一个无法验证的状态，最终一定会是错的。

## 15.4 电平：在 ADC 处削波，而不是在软件里

曾经叠了两级增益：ES8311 的 PGA +30 dB，服务器的软件 `tx_mic_db` +12 dB。服务器报告 5% 的
TX 样本削波，而设备报告 `peak=32768`——在 ADC 处就已是满量程，任何软件之前。

那个有用的负结果：把服务器增益降到 +3 dB，削波从 5.0% 变成 **5.8%**——峰值本来就已经顶在
ADC 的天花板上。把 `tx_mic_db` 设成 0（恒等，`audio_levels.py` 的写法）得到 `peak=40%` 与
零个新的削波样本，因为电平从来不是服务器能修的东西。

| 电平目标 | 值 | 理由 |
| --- | --- | --- |
| 语音 ADC 峰值 | **20000–29000**（32767 的 60–88%） | 给最响的音节留余量，又不损失量化精度 |
| MIC 30 dB 实测 | 27 522（84%） | 本机的参考点 |
| MIC 36 dB 实测 | 32 768（削波） | "更响总是更好"的那一步长什么样 |
| 服务器软件增益 | 0 dB | 对已量化的样本做缩放，换不回余量 |

模拟 PGA 是唯一正确的买电平的地方：它在 ADC 之前，因此能提升 SNR。软件增益只是把已经量化
的东西重新缩放，所以那一步看起来像 +6 dB 的操作，其实除了削波什么也做不到。

## 15.5 计数器必须显示什么

发射以证据验收，不以印象验收（第 `00` 章 §V1）。每次发射一行的验收行：

```
tx done: frames=<n> sendfail=<n> readfail=<n> peak=<n>
```

要求的取值，且必须在同一次运行里测得：

| 字段 | 要求 | 2026-11-22 参考运行 |
| --- | --- | --- |
| `frames` | ≈50 × 秒数，说明节拍在整段发射里都成立 | 30.5 秒内 1500 帧 = 50.0/s |
| `sendfail` | 0 | 0 |
| `readfail` | 0 | 0 |
| `peak` | 语音 20000–29000 | MIC 30 dB 时 27 522（36 dB 时 32 768 = 削波） |
| `send_max`（profile 行） | 移动链路 ≤50 ms，局域网 ≤17 ms | 移动链路 27.9 ms，`slow=0` |
| 窗口内 W/E 日志行 | **0** | 0 |

`sendfail` 非零而 `readfail` 干净，说明上行是被下层掐住了（AD-004 的地盘）。`sendfail`
非零**且**出现 W/E 行，说明会话在死，而 PTT 指示灯只是症状，不是故障本身。

**`peak` 需要说话，不是按键。** 无人值守的发射量到的是静音，报出的峰值自然很低
（2026-11-23 无人说话时实测 835）——那是方法问题，不是电平问题。通路可以无人证明
（256 帧、零失败），电平不行。查电平的姿势是：有人对着麦克风说话，另一个人读那行日志。

## 15.6 已知边界

记下来，是为了下一次调查不要把它们当成意外重新发现一遍：

- **没有重传。** 丢掉的上行帧就是没了，电台的音频上就有一个 20 ms 的洞；重传会推迟之后每一帧。
- **固件不执行 TOT。** 服务器 120 秒上限与电台自己的 TOT 才是限制；按 2 分钟的验收实验会在
  服务器上限处被切断，那是正确行为，不是故障。
- **半双工依赖服务器。** 键控期间服务器是否发送下行音频不由设备控制（AD-004）；设备只能丢弃
  它用不上的。一个在发射时恢复下行的服务器，即使 100 ms 超时还在，故障也会回来。
- **削波可以从 PGA 回来。** MIC 档位是能挺过重启的用户设置（AD-006）；为弱信号把它调高可能
  把 `peak` 推过 29000，而唯一正确的应对是降档，不是在下游补偿。
- **活性是服务器的判断。** 固件无法知道服务器是否仍把它当作 keyer；它只能察觉自己的 socket 在死。
