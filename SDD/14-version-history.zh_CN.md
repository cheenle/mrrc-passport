# 14. 版本历史

新的在上。这是**证据账本**，不是 changelog：给用户看的发布说明在 `../docs/CHANGELOG.md`，
那些说明刻意不含假设、死路和反证数字。这里的每一行都有，因为一次修复里最有用的部分，是那些
"其它解释被排除"的记录。

行格式（第 `00` 章 §V4）：**症状 → 当时的信念 → 测量显示了什么 → 根因（文件:函数）→ 修法 →
实测结果 → 边界，即"没做什么"。**

| 2026-11-22 | 2026-11-22 | pi | **耗 CPU 的是重绘，不是面板（第 05 章 §5.4）。** ① 症状：`taskLVGL` 56–61%、`IDLE` 7–14%——对一块 5.26 Hz 的 240×320 面板来说太高。② 当时的信念：先怀疑面板 SPI 带宽，再怀疑瀑布。回答的是两台仪器：`bsp_display_flush_stats()` 显示 526 KB/s（3.5 屏/秒），`bsp_display_flush_bands()` 把它定位到"每段"代价。③ 测量显示：冻结轨迹掉了 25 个 CPU 点，而它只占刷新面积的四分之一——是每段，不是每像素。④ 根因：`mrrc_ui.c` 每次扫描 240 个近似单像素的线段，每段都有各自的 LVGL 管理开销。⑤ 修法：120 个顶点、间距 2 px、线宽 3；刷新 526 → 344 KB/s、flush 85 → 56 次/秒、`taskLVGL` 42 → 28–30%、`IDLE` 29 → 42–45%。⑥ 结果：为随后的网络工作腾出了预算余量。边界：线宽 2 实测相同，说明线宽不是剩余成本；S 表与 chips 没动，因为冻结它们各自只有 ≤5 点。 |
| 2026-11-22 | 2026-11-22 | pi | **瀑布内存：8 位调色板索引（AD-005）。** ① 症状：`s_wf_buf` 占 19 200 B `.bss`——最大单块——面对 16 KB 握手底线与 27–42 KB 的 `largest`。② 当时的信念：必须砍历史长度才能换内存。③ 测量：历史是 40 行 × 240 px；RGB565 每像素 2 B，索引每像素 1 B 加 1 024 B 调色板。④ 根因：像素格式，不是历史长度。⑤ 修法：`uint8_t` 索引 + `lv_canvas_set_palette`，`heat_init()` 在第一个消费者之前填好色带。⑥ 结果：19 200 → 10 624 B、`free` 48 → 57–59 KB、`largest` 27–42 → 38–48 KB，代价 1–2 个 CPU 点。边界：轨迹路径仍用 RGB565（4 B 点以 240 Hz 刷新很便宜）；把两种格式统一就会把 19 200 B 带回来。 |
| 2026-11-22 | 2026-11-22 | pi | **多个网络，按音频健康度选择（AD-007）。** ① 症状（火车上、手机热点）：丢包 6.5–12%、RTT 峰值 6–10 秒、四分钟里有一秒出现 26–41 个 ping；音频卡顿、会话掉线。② 当时的信念：靠缓冲扛过去，以及 RSSI 是可用的代理量。两者都被否证：十秒 32 KB/s 是 320 KB，而 SRAM 只有 400 KB；一个 −25 dBm 的接入点实测在丢约 10% 的包。③ 根因：每个 station 接口只能配一个 AP，且没有任何指标反映**音频**健康。④ 修法：三组 (SSID, 密码)（NVS/Kconfig），开机优先上次可用，切换由持续音频劣化触发。⑤ 结果：会话在原先会掉线的场景下存活；帧会丢，socket 不丢。边界：不声称连续性——书面目标是优雅降级；迟滞阈值仍是未决问题，住在代码里而不是这张表里。 |

## 这个账本不是什么

- **不是发布历史。** tag、用户可见功能与升级说明在 `../docs/CHANGELOG.md`；这张表做 changelog
  很差，而好的 changelog 做账本也很差。
- **不完整。** 只有产出了"值得不重新推导"的测量的轮次才有行。平淡的改动不占一行，而没有行
  不代表什么都没发生。
- **不能原地改。** 错误的行靠追加修正：写上新日期与取代它的那次测量（第 `00` 章 §V4）；旧数字
  保持可见，因为"我们曾经相信过它"本身也是记录的一部分。
