# 00. 校验纪律（本地增补）

> **状态：规范性。** 本章没有 ART 码，因为 TeamSD 没有定义它：这是本项目的增补。它的
> 优先级高于其余任何一章。本文档其他位置若有任何陈述满足不了 §V1，那它就不是设计陈述，
> 而是愿望，必须标成 `proposed`。

## 0.1 为什么需要这一章

本仓每一次昂贵的故障都是同一个形状：**一个在没人写下来的条件下才成立的数字。** 三个
真实例子：

| 当时的信念 | 实测 | 这个差异的代价 |
| --- | --- | --- |
| "峰值有 23000，编解码器没问题" | 48 kHz 采集峰值 **468/32767**；16 kHz 是 12708 | 三天在软件里追一个"麦克风太小" |
| "设备只收到 28 KB/s，说明链路就这带宽" | 同一个 AP 上参考客户端拿到 **50.2 KB/s** | 两轮加大缓冲，什么都没改变 |
| "PTT 自己松开，那是按键问题" | 按键按住 **16.5 秒**无释放事件；`sendfail=71/78` | 在没看 socket 之前先重做了一遍按键处理 |

这三次里，修都便宜，**发现**才贵。本章存在的目的，是让那次发现活得比发现它的人久。

## 0.2 规则

每条规则都是对"往 SDD 或提交信息里写结论的人"的义务。

| ID | 规则 | 违反的形态 |
| --- | --- | --- |
| **V1** | 每条量化陈述都要写明**测量点**（产出它的计数器、日志行或命令）、**日期**与**场景**（链路类型、会话时长、当时还在跑什么）。 | 一个数字缺这三样中的任何一样。 |
| **V2** | 一次测量必须能区分至少两种解释，否则它只是观察，不是证据。 | "现在好了"，且没有任何东西能证明"不好"时会不同。 |
| **V3** | **负结果也是结果**，要用同样的认真记录。 | 把一个假设删掉，而不是在纸上否证它。 |
| **V4** | 纠正是**原地且带日期**的。修订 AD（`⑧ …`）、把某行改写成"曾 → 今"、把结论降级；删掉一个错结论时，必须写明它为什么错。 | 错误陈述悄悄消失在一个 git diff 里。 |
| **V5** | 状态是阶梯，不是自由形容词：`proposed` → `accepted` → `implemented` → `field-exercised` → `hardware-verified`。升级必须拿出对应那一级的物证。 | "设计文档存在"被当成"已实现"。 |
| **V6** | 没有条件的数字是传闻。吞吐、延迟、CPU 的结论必须带上窗口与流量。 | 写 `50 帧/秒` 却不说持续多久、当时还跑了什么。 |
| **V7** | 改动测量工具本身会让它的历史失效。跨计数器改版做比较之前必须重量一遍。 | 新旧数字被塞进同一张表且不加注释。 |
| **V8** | 测量与理论冲突时，测量赢；两个测量互相冲突时，**先找出条件差异**。 | 把其中一个当成"错的"丢掉，却没定位差异。 |
| **V9** | 无法再复测的结论（工具被移除、单元不在手边）标成 `historical`，绝不留着当现状。 | 拿 2026-11 的数字当作今天的板子状态。 |

## 0.3 三台仪器

这块设备上没有任何单一仪器能区分"链路差"与"设备慢"——而正是这个歧义造出了 §0.1 的前
两个例子。所以任何传输类结论至少要用到下列中的两个：

| # | 仪器 | 它能证明什么 | 位置 |
| --- | --- | --- | --- |
| 1 | **设备 profile 行**（`CONFIG_MRRC_PROFILE=y`）—— `link: rx=… underruns=… wr_max=… rebuf=… rssi=…`、`ws: total=…`、`txlink: send_max=… slow=… stalls=…` | 设备实际做了什么：环占用、写阻塞、丢弃 | `main/mrrc_audio.c`、`main/mrrc_net.c`；出货默认关闭（guardian 规则 `diagnostics-not-shipped`） |
| 2 | **服务器计数器** —— `TX session: frames=… fed=… written=… queue_drops=… peak=…`、`Terminal media losses: … max pump stall …` | 服务器发了什么、它的写阻塞了多久 | 服务器侧；所有者是 `mrrc_modern/SDD/` |
| 3 | **参考客户端** —— 同一个 AP 上第二条 `/WSterminal` 客户端 | 那一刻网络到底能承载多少 | 手工，记录在传输日志里 |

传输那一轮留下的经验法则：**参考客户端正常而设备不正常，就别再看网络了。**

## 0.4 反复校验的回路

长会话是唯一能抓到漂移的仪器，而漂移是这里的主要失效模式：快 0.16% 的时钟、每秒丢 2%
的环形缓冲、每分钟涨 40 字节的缓冲。凡是碰音频、发射、内存的改动，都必须走这个回路：

1. **短跑（≤1 分钟）**——能跑起来吗？便宜，但关于稳定性什么都证明不了，也绝不能当作
   稳定性的证据引用。
2. **持续跑（≥10 分钟，最好 30+）**——真正找出故障的那些测试：13 分钟 soak 看到
   `drops ≈ 57/min`；30.5 秒发射看到 `frames=1500 sendfail=0`。注意时钟漂移那条故障
   （`docs/design-v1.md` 3.2）明确**不能**用短会话证明。
3. **逆境跑**——同一份代码放到移动链路上（丢包 6.5–12%，RTT 峰值 6–10 秒）。过了这一关
   才是"能用"，之前只是"实验室里能用"。
4. **把发现变成回归线**——抓到故障的那个计数器要进验收行，故障才无法悄悄回来。这也是
   guardian 的规则大多是计数器和上下界、而不是散文的原因。

## 0.5 一次纠正长什么样

三种形式，都让错的东西保持可见：

- **AD 修订** —— 新事实以 `⑧`、`⑨` 追加在原 AD 下，带日期和改变决策的那次测量。AD 号
  永不改变；修订记录的是这个决策的**历史**。
- **带"曾 → 今"的行改写** —— 如 `08` AD-005 的内存表。旧值留在同一个单元格里，决策的
  代价才一直可读。
- **降级** —— 证据被撤回时，状态沿 §V5 阶梯下移，并写明是树上的哪一枝失去了支撑。

## 0.6 执行

这些规则是散文，所以在散文能起作用的地方执行：

- **guardian**（`../.agents/skills/sdd-guardian/`）承载可机械检查的那部分后果——超时上界、
  调色板顺序、单 socket——它的 `selftest` 在规则、夹具或引用过期时失败；
- 同一个 `selftest` 里的 **SDD 结构测试**拒绝违反本文档形式的章节：没有验证方法的 NFR 行、
  缺 `Problem`/`Rationale`/`Consequences` 的 AD、不是倒序的版本历史、引用 `待写` 章节；
- 其余靠评审。评审者要问的，正是这一章被写出来的那个问题：**"那个数字在什么条件下成立，
  万一你错了，什么东西会不一样？"**
