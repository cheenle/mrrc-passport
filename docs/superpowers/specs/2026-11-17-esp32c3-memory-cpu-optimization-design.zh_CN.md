# ESP32-C3 内存与 CPU 优化设计

## 背景

MRRC 终端现在用一条 `/WSterminal` 连接承载控制、下行音频和上行 PCM。去掉第二条
常驻音频 TLS/WebSocket 是一次有效的内存优化，但新的 240×54 RGB565 频谱瀑布把
大部分收益又吃掉了。

实现必须保留完整的频谱与瀑布呈现。服务端协议、单连接架构、16 kHz codec 与 PTT
行为不在本优化范围内。固件里没有任何编解码库：`main/mrrc_audio.c` 把 Int16 PCM
直接交给 ES8311，所以本文档过去为 micro-opus 伪栈预留的预算已经不存在了。

## 状态：实际交付了什么（2026-11-20，v1.2.0）

四个阶段都落地了，而且真机上有两个发现与当初写计划时的假设相反。

| 阶段 | 结果 |
| --- | --- |
| 1. 确定性缓冲复用 | 落地。下行原地抽取；上行用一块带标签的包缓冲。 |
| 2. 任务与套接字内存 | 落地方式不同：`AUD_TASK_STACK` 是 8,192 B，但 `/WSterminal` 缓冲**升**了 4,096 → 8,192 B。4 KB 的接收缓冲会反压 socket：服务端实测到 5.8 s 的 pump stall。更小并不更好。 |
| 3. 8 位索引瀑布 | 落地（`main/mrrc_scope.c`），240×54，完整 Jet 调色板。 |
| 4. 刷新与碎片控制 | 落地。`BSP_LVGL_DRAW_BUFFER_LINES` 是 **24**，不是 8：LVGL 改用系统堆之后，绘制缓冲不再是约束。 |

给后来读这份文档的人两条更正：

- **这块板跑的是 ESP-IDF 5.5.3，不是 5.4.2。**
- **`CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM` 必须保持关闭。** `lvgl/lvgl` 的约束是
  `^9.5.0`，实际解析到 9.6.x；9.6 把 `LV_ATTRIBUTE_FAST_MEM` 加到了多得多的绘制
  代码上，打开这一项会把约 117 KB 搬进 SRAM。C3 的 IRAM 与 DRAM 是同一块 400 KB，
  于是 DRAM 从 170 KB 涨到 287 KB、启动堆从 201 KB 掉到 88 KB，
  `esp_wifi_init()` 报 `ESP_ERR_NO_MEM`，设备无限重启。

## 当前实测状态

2026 年 11 月在真机上测得，ESP-IDF 5.5.3、`-O2`、
`CONFIG_LV_ATTRIBUTE_FAST_MEM_USE_IRAM` 关闭：

| 指标 | 数值 |
| --- | ---: |
| DRAM 已用 / 总量 | 179,022 / 321,296 B（55.7%） |
| Flash 代码 | 1,175,482 B |
| 启动堆 `free` / `largest` | 201 KB / 112 KB |
| 起网之后的堆 | 119 KB / 104 KB |
| 稳态 `free` / `largest` | 46–49 KB / 30–32 KB |
| 音频环 / WS 接收缓冲 | 16,384 B / 8,192 B |
| LVGL 绘制缓冲 | 24 行（11,520 B） |
| 稳态音频丢帧 | 约 2%（`err=0`），仍未结案 |

## 写这份计划时的基线

下面的数字来自最初的计划，只作为历史保留；它描述的是一版已经不存在的 Opus 时代
固件。

当时的基线：

| 指标 | 当时值 |
| --- | ---: |
| 运行期 `free` | 34 KB |
| 运行期 `largest` | 11 KB |
| 音频计数 | `err=0 drop=39` |
| 音频任务栈 | 分配 12,288 B，最小剩余 9,668 B |
| `libmain.a` `.bss` | 53,364 B |
| 瀑布 framebuffer | 25,920 B |
| LVGL 绘制缓冲 | 2 行 / 960 B |

工作区当时正在频繁变动。采集这份基线之后，8 KB 音频栈与 8 行 LVGL 的实验已经出现在
工作区里，还夹着与网络配置无关的改动。实施任何阶段之前，先重读 `git diff` 并重新
采集运行期基线。保留所有并行进行的工作，不要重复或覆盖已经在做的实验。

频谱之前的一次运行期测量是 `free=41K`、`largest=17K`、`drop=2`。这是回退信号，
而不是某一项改动的证据。因此所有性能结论都必须用 A/B 运行期实测来确认，不能只从
MAP 推断。

## 目标

- 保留完整的频谱与瀑布呈现。
- 在不改动服务端的前提下，把稳态内存减少约 20 KiB。
- 降低瀑布拷贝与 LVGL flush 的开销。
- 在可比网络条件下，把音频丢帧恢复到频谱之前的水准。
- 改善 `largest` 与 PTT 期间的最小堆，而不只是总 `free`。
- 每一项高风险改动都要能独立测试、独立回退。

## 非目标

- 不改服务端或协议。
- 不改 codec 采样率，也不在运行期重新配置 codec。
- 不缩小瀑布尺寸、调色板或频谱内容。
- 不引入新的音频编解码器；线上格式两个方向都是 PCM16。
- 不移除频谱/瀑布，也不把它挪到单独页面。
- 第一阶段不重写 cJSON 处理。

## 选定方案

分阶段优化。先回收确定性内存并测量结果，然后把瀑布存储与渲染换成 8 位索引环形缓冲。
在回收足够内存之后再恢复 LVGL 绘制缓冲到 8 行，并把音频丢帧与渲染开销与当前的两行
实现对比。

### 预期内存预算

| 改动 | 预期内部 RAM 影响 |
| --- | ---: |
| 原地完成 48 kHz → 16 kHz 抽取 | +1,920 B |
| 单一对齐的上行采集/升采样/打包缓冲 | 约 +2,559 B |
| 8 位瀑布替代 RGB565 | +12,960 B |
| 240 列频谱接收双缓冲 | 约 +610 B |
| 音频任务栈 12,288 B → 8,192 B | +4,096 B，以实测为前提 |
| `/WSterminal` 缓冲 4096 → 2048 | +2,048 B，以实测为前提 |
| LVGL 绘制缓冲从 2 行恢复到 8 行 | −2,880 B |
| **预期净效果** | **约 +21.3 KB** |

这些是源码/MAP 层面的估算，不是运行期的保证值。对齐与堆布局会改变最终数字。

## 阶段 1：确定性缓冲复用

### 下行抽取

`main/mrrc_audio.c` 当时同时持有 `s_pcm48` 与 `s_pcm16`。改为原地抽取进 `s_pcm48`：
输出索引永远不超过输入索引，所以不会覆盖尚未读取的样本。把同一块缓冲与解码后的输出
长度交给 `bsp_audio_write()`，并删掉 `s_pcm16`。

### 上行打包

`main/mrrc_tx.c` 当时分别用 `mic`、`up` 和带标签的 `frame` 三块数组。改为一块对齐的
`int16_t` 缓冲：

1. 读 320 个单声道样本到缓冲开头。
2. 从样本 319 往样本 0 反向展开，使每个输入样本变成三个输出样本，且不覆盖未读的输入。
3. 把 1,920 字节负载整体后移一个字节并插入传输标签。
4. 精确发送 1,921 字节，并且只有整包被接受时才计一帧。

用仓库之外的临时主机程序验证全部 320 个输入位置、负样本、边界值以及最终带标签的
字节布局。不要为此在仓库里新增常驻测试框架。

## 阶段 2：任务与套接字内存的条件性调整

把 `AUD_TASK_STACK` 从 12,288 降到 8,192 B，作为独立实验。运行期高水位显示只用了
约 2.6 KB，但更早的一份 8 KB 溢出报告必须当作矛盾结果对待。不要进一步降到 6 KB。
在验证过程中覆盖正常解码、PLC、PTT、重连与频谱渲染，并记录栈高水位。

只有在确认当前全部流量都装得下之后，才把单条 `/WSterminal` 缓冲从 4096 降到 2048：

- 上行包：1,921 B 加协议开销；
- 频谱负载：约 852 B；
- 较大的控制 JSON：由现有累积器重组。

部分发送或发送失败都不得计为一次成功的音频帧。

## 阶段 3：8 位索引瀑布

### 存储

把 `uint16_t s_wf_buf[240 * 54]` 换成 `uint8_t s_wf_buf[240 * 54]`。每个字节是既有
64 项 Jet 调色板的索引。调色板本身仍是 RGB565，只占 128 字节。

显示仍然把每个像素渲染成 RGB565。改变的只是历史数据的持久表示。

### 环形布局

保留"最新行索引"而不是每次更新都搬 25 KB：

- 每次刷新写入一行 240 字节的调色板索引；
- 最新物理行按 54 取模前进；
- 渲染器把显示行 `y` 映射到 `(newest_row + 1 + y) % 54`，得到从旧到新的顺序；
- 不再有整块瀑布的 `memmove`。

移除当前在收到新频谱帧时额外做的那次瀑布平移。每个刷新 tick 只写一行（含插值的那行）。

### LVGL 渲染

用独立的 scope 模块，而不是继续往 `mrrc_ui.c` 里堆渲染代码：

- `main/mrrc_scope.c` 负责频谱降采样、环形存储、调色板查表与自定义瀑布绘制回调；
- `main/mrrc_scope.h` 暴露初始化、频谱喂入与刷新；
- `main/mrrc_ui.c` 创建 scope 对象并调用该模块；
- `main/CMakeLists.txt` 注册新源文件。

瀑布使用自定义 LVGL 对象绘制事件。在 `LV_EVENT_DRAW_MAIN` 期间，它只把当前裁剪区内
的像素从 8 位调色板索引转换成 LVGL layer 里的 RGB565。必须遵守 layer stride 与裁剪
矩形，且不得分配整块 RGB565 中间缓冲。

这条直通路径只在 RGB565 layer 下成立。若 LVGL 给出其它格式，走 LVGL 支持的颜色写入
路径，而不是做无检查的强制类型转换。绘制回调里不允许持久分配。

频谱曲线继续使用既有的点数组。当前 LVGL 版本只保存点指针而不拷贝，因此不需要第二块
点缓冲。

### 频谱喂入

在 WebSocket 回调里把 850 个 bin 降采样成 240 列，写入两块 240 列缓冲之一。只有整帧
写完之后才切换。这去掉了 850 字节的常驻原始数组，净省约 610 B，并防止 UI 读到两帧
频谱混在一起的数据。

WebSocket 回调不得访问 LVGL 对象。

## 阶段 4：刷新与碎片控制

在前述内存回收之后，把 `BSP_LVGL_DRAW_BUFFER_LINES` 恢复到 8。对 2 行与 8 行两个
构建比较音频丢帧、UI 响应与 CPU。如果丢帧仍然偏高，不要为了那 2,880 B 死守 2 行。

减少不必要的 LVGL 字符串分配：

- 只在显示的百分比变化时重绘电量标签；
- 只有某个被显示的电台字段真的变了才推进 UI 序号；
- 不要去替换格式化文本没有变化的标签。

第一轮实现不要替换 cJSON。如果上述工作之后 `largest` 仍低于 17 KB，再统计 cJSON 的
分配次数，然后考虑为已知控制 schema 写一个不分配的小解析器。

## 验证

### 构建与静态测量

- 用 ESP-IDF 5.5.3 与 `-O2` 构建当前源码。
- 与基线对比 `libmain.a` 的 `.bss`、总 DRAM 与固件大小。
- 确认没有凭证或本地 `sdkconfig` 的值进入被跟踪的文件。

### 临时主机检查

用仓库之外的一次性主机程序验证：

- 原地抽取；
- 反向原地 3 倍升采样与标签布局；
- 瀑布环形行映射在回绕处；
- 频谱双缓冲发布。

### 真机检查

每个高风险阶段采集 60 秒的运行期记录：

```text
free / largest / min / dma_free
audio frames / err / drop
audio stack high-water mark
PTT keys / frames / sendfail / readfail / last event
```

验收标准：

- `err=0`，且丢帧没有无法解释的增长。
- 前后对比的听感测试回到频谱之前的水准；目标是可比六分钟窗口内不超过 2 次丢帧，
  而不是跨变化网络条件的绝对保证。
- 没有 Guru Meditation、task watchdog 或部分发送记账错误。
- 压力测试后音频任务栈高水位仍保有 2 KB 以上余量。
- 运行期 `largest` 尽量不低于 17 KB，且永远不低于仓库下限 8 KB。
- PTT 被对方清晰听到一次，松开后接收音频正常。
- 瀑布保持 240×54、完整 Jet 调色板与正确行序。

阶段检查通过后，做 30 分钟接收测试与十轮 PTT。记录每一轮的 RX-idle、TX-ready 与
松手后 `free/largest/min`。

## 回退边界

- 任何栈回归都把音频栈退回 12 KB。
- 任何收发回归都把 WebSocket 缓冲退回 4096。
- 只有在裁剪、颜色或绘制耗时不对时才回退自定义瀑布渲染器；独立的缓冲复用改进保留。
- 即使需要放弃其它可选优化，也要把 LVGL 恢复到 8 行。

## 最终实施约束

未经当时明确的许可，不烧录任何固件。编译成功与 MAP 改善都不是真机验证。
